# T-0024 · fix(shell): time out the shell's git calls

## Why

Every git call the shell makes goes through `git()` in `apps/desktop/src/main/kit/source.ts`, and none has a time limit. A hung `git fetch` (opening a repo runs `fetchRepo`) waits forever, and a hung read stalls the Now watcher's whole tick. Most reads also swallow every error (`.catch(() => null)`), so a read that did fail would look like a missing file. One such hang already blocked CI (BACKLOG Parked, 2026-11-25, seen on T-0016).

## Acceptance criteria

Each one is checked by something that can be run or looked at. No criterion without a check.

- [x] A1: Every git call in `source.ts` has a limit, set in one place: 10 s for a read and 60 s for `fetchRepo`. Each limit can be overridden by `RIVETARI_GIT_READ_LIMIT_MS` / `RIVETARI_GIT_FETCH_LIMIT_MS`, read at call time. A call that passes its limit kills git and rejects with `git <subcommand> timed out after <N> s`. The promise settles at the limit even when git's child processes keep its pipes open. `source.ts`'s catch-alls pass a timeout on instead of treating it as "not there" · check: read `git diff origin/day/2026-11-25 -- apps/desktop/src/main/kit/source.ts`, plus A2 and A3

## Constraints

For a fetch, add it as an extra remote on a `kitFixture()` repo (`fetchRepo` runs `--all`). - `kit-fixture.ts` is used as it is, only through its exports.

## Decisions

Appended by the session, one line each, newest last.

- 2026-11-25: Limits: decided for the owner: 10 s per read, 60 s for a fetch (alternative: one 30 s limit for both, or a 20 s fetch so a CI hang fails inside vitest's 30 s). The fetch test makes many git reads plus a local fetch and takes 515–656 ms locally and 961 ms in CI (T-0016), so one read takes well under 100 ms. 10 s gives a read over 10× the whole test's slowest run. A real fetch goes over the network to a remote of any size, so 60 s leaves room for a slow link and still bounds a hang.
- 2026-11-25: How the tests hang git: decided for the owner: real git against a local server that never answers, for both a fetch and a partial-clone read (alternative: an injectable runner that spawns a hanging `node` process). It tests the real kill-and-settle path, and partial-clone reads can really hang this way.
- 2026-11-25: How tests set short limits: decided for the owner: `RIVETARI_GIT_READ_LIMIT_MS` / `RIVETARI_GIT_FETCH_LIMIT_MS`, read at call time (alternative: an exported mutable limits object, which the e2e couldn't reach). `launchApp({ env })` already passes env to the main process.
- 2026-11-25: "The Fetch button recovers": decided for the owner: no button is added. Opening the repo again re-runs the fetch and clears the message (alternative: add a Fetch button, a new UI feature beyond the spec's fix).
- 2026-11-25: The renderer drops a late fetch result for a repo that's no longer selected. Decided for the owner, because the spec asks for the message in _the repo's_ box, and a 60 s timeout makes a stale message on the next repo likely (alternative: leave `App.tsx` alone and accept the stale message).

- 2026-11-25: The stale-fetch guard: decided for the owner: a counter of openings in a `useRef` beside `handleSelect`; only the latest opening's fetch may set the error box (alternative: compare the failed fetch's path with the selected repo, which would still let a late failure from an earlier opening of the same repo replace a recovered one).
- 2026-11-25: A4's "recovers" in the e2e: decided for the owner: the hanging remote's URL is pointed at the fixture's origin ("the remote answers"), and a gated draft pushed there showing as "5 waiting" proves the reopened fetch succeeded (alternative: only assert the error box is gone, which a cleared-on-open message passes without any fetch).
- 2026-11-25: Test teardown: decided for the owner: destroy the hang server's sockets, then retry removing the temp folders for up to 10 s, since on Windows a cut-off git child still running in the repo blocks the removal and `rmSync`'s `maxRetries` didn't retry it (alternative: kill git's process tree, out of scope; parked).
- 2026-11-25: Sent back by the foreman: `desktop-e2e` red on PR #41 (fetch-timeout teardown hangs on Ubuntu); `ci` itself was green but this card rests on the e2e.
- 2026-11-25: Cause of the Ubuntu hang: a timed-out fetch killed only `git`; its sub-fetch and `git-remote-http` kept running, connected to the hang server, and Playwright's `app.close()` waits for the Electron process's pipes to close, so the `afterEach` (which cut the server's connections only after closing the app) waited forever. Seen: the orphaned processes in a `node:22` container (3 left after `child.kill()`); that they hold the app's pipes is inferred from Playwright waiting on `close` (not `exit`), and confirmed by the next CI run, where the app closed at once.
- 2026-11-25: Killing the tree, though "Out of scope" named it: the foreman's send-back put it in scope as the product fix. Decided for the owner: on POSIX git runs in its own process group and a timeout sends the group SIGTERM, then SIGKILL after 5 s; on Windows `taskkill /pid <pid> /T /F`, the approach of the engine's `killTree`, written inside `source.ts` since the desktop app doesn't depend on the engine (alternative: only reorder the teardown, leaving orphaned git processes in the product). The Parked [product] line on this is now fixed by this card.
- 2026-11-25: `git()` moves from `execFile` to `spawn`, because `execFile` drops `detached` (seen in the container: git stayed in the caller's group). Decided for the owner: a failure keeps `execFile`'s message, `Command failed: git <args>` plus git's stderr; stdin is ignored rather than an unused pipe; stdout over 16 MiB stops git with a RangeError, as `maxBuffer` did (alternative: keep `execFile` and find git's children through `ps` on a timeout).
- 2026-11-25: Proof of the kill: decided for the owner: both timeout tests (unit and e2e) now check that every connection to the hanging remote closes after the timeout, which fails against the old `child.kill()`, and the e2e teardown closes the server before closing the app (alternative: only reorder the teardown, which would hide a leaked tree). The test servers read and drop what git sends, because on Linux a paused socket never sees the peer's end (CI run 45691419546 failed on exactly that; reproduced in the container).
